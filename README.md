## Виконані завдання

### 1. Setup і typed-схема

- Підключення до локального PostgreSQL через `pgserver` і виведення версії сервера.
- Завантаження шести CSV до raw-таблиць і перенесення в typed-таблиці через `INSERT ... SELECT`.
- Використання `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`, `NOT NULL` та індексів.
- Для відгуків використано технічний identity-ключ `review_row_id`, оскільки джерельний `review_id` не є надійним унікальним ключем.
- Порівняння кількостей рядків raw і typed після типізації.

### 2. DML

- `INSERT ... RETURNING` — створення alert щодо затримок доставки.
- `INSERT ... ON CONFLICT DO UPDATE` — повторюване оновлення `seller_score`.
- `UPDATE ... FROM` — розрахунок прапорця запізнення `is_late`.
- `DELETE ... RETURNING` — контрольоване видалення старих alert-записів (у зафіксованому запуску видалених рядків немає).

Рейтинг продавця обчислюється після дедуплікації до рівня **`seller_id × order_id`** і попереднього агрегування відгуків до рівня замовлення. Це усуває множення оцінок через кілька позицій одного замовлення. Якщо в одному замовленні кілька продавців, order-level review усе одно відноситься до кожного з них — це обмеження прийнятої навчальної моделі.

### 3. Сегментація покупців

- Створення `olist_customer_dim` з ключем `customer_unique_id`.
- Створення `customer_segments` з identity PK, FK, `UNIQUE`, `CHECK`, `NOT NULL`, `DEFAULT`.
- Ідемпотентне наповнення через `INSERT ... SELECT ... ON CONFLICT DO UPDATE`.
- Обчислення recency відносно максимальної дати покупки в датасеті плюс один день, а не поточної системної дати.

| Сегмент | Покупців |
|---|---:|
| `regular` | 45 982 |
| `inactive` | 40 032 |
| `new` | 8 891 |
| `VIP` | 1 191 |
| **Разом** | **96 096** |

### 4. JOIN і бізнес-інтерпретації

Підготовлено п’ять запитів із бізнес-питаннями, SQL-кодом, фактичним результатом та інтерпретацією:

- `INNER JOIN` — виторг за категорією товару та штатом продавця.
- `LEFT JOIN` + `COALESCE` — ознаки реального покупця.
- `FULL OUTER JOIN` — порівняння штатів покупців і продавців.
- `SELF JOIN` — пари продавців із різних міст одного штату.
- Anti-join — замовлення без відгуків.

### 5. Агрегування, множинні та віконні операції

- `GROUP BY` / `HAVING` — дохід за товарними категоріями та середній чек (`AOV`) за штатами.
- `STRING_AGG` — список різних категорій покупок для кожного `customer_unique_id`.
- `UNION` і `INTERSECT` — порівняння наборів штатів.
- `ROW_NUMBER() OVER (PARTITION BY ...)` — останнє замовлення кожного реального покупця.

Notebook завершується Reflection обсягом **227 слів** і підсумковими SQL-перевірками.

## Особливості інтерпретації

- `customer_id` позначає запис клієнта, пов’язаний із конкретним замовленням, а `customer_unique_id` використовується для агрегації на рівні реального покупця.
- `review_id` у джерельних даних може повторюватися, тому primary key таблиці відгуків — `review_row_id`.
- `COALESCE(avg_review_score, 0)` у прикладі feature engineering заповнює відсутнє значення для аналітичної таблиці; нуль не є справжньою оцінкою за п’ятибальною шкалою.
- Дата останньої покупки та RFM-подібні сегменти залежать від історичного періоду Olist і не повинні інтерпретуватися відносно сьогоднішньої дати.
